# Тихий хороший день

Небольшая текстовая игра о мягком ритме жизни, простых решениях и спокойном дне.

Игрок проходит три главы, выбирая реплики и действия. Каждый выбор меняет три характеристики —
**Забота**, **Связь**, **Покой** — и от их соотношения зависит, какой концовкой закончится день.

## Стек

- React 19 + TypeScript
- Vite 8
- Tailwind CSS v4 (токены дизайн-системы в `@theme`)
- react-router (HashRouter)

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
```

Остальные команды:

```bash
npm run check       # всё сразу: типы + линт + формат + тесты
npm run build       # check + продакшен-сборка в dist/
npm run preview     # локальный просмотр собранной версии

npm run typecheck   # tsc -b
npm run lint        # eslint
npm run format      # prettier --write (переформатировать)
npm run format:check # prettier --check (только проверить)
```

`npm run check` — то, что стоит запускать перед коммитом: он же встроен в `build`.

## Соглашения по коду

Всё, что можно проверить машиной, проверяет линтер — нарушение валит `npm run lint` и
вместе с ним `npm run check`. Заучивать список не нужно, достаточно прогнать проверку
перед коммитом. Ниже он приведён целиком, включая автоматические правила: полезно понимать,
почему они именно такие. Правила описаны в [eslint.config.js](eslint.config.js).

### Компоненты

**Объявление — `function`, экспорт — именованный.** Проверяется линтером (`func-style` и
запрет `ExportDefaultDeclaration`).

```tsx
// да
export function Card({ title }: Props) {}

// нет
export const Card = ({ title }: Props) => {};
export default function Card({ title }: Props) {}
```

Стрелка в `const` и `function` отличаются по сути только всплытием, но третий способ
записать одно и то же ничего не даёт, а разбирать разнобой глазами приходится каждый раз.
Default-экспорт запрещён отдельной причиной: он позволяет импортировать компонент под
произвольным именем, из-за чего поиск по кодовой базе перестаёт находить все использования,
и мешает автоимпорту в IDE.

Правило смотрит только на объявления — стрелочные функции в колбэках (`onClick={() => …}`,
`useCallback`, `map`) остаются как есть.

**Один компонент на файл, имя файла = имя компонента.** Это соглашение не проверяется
автоматически, но из него следует правило про `Props` ниже.

### Типы

**Тип пропсов — отдельный `type Props` прямо над компонентом.** Инлайновый объектный тип
в параметре запрещён линтером.

```tsx
// да
type Props = {
  title: string;
  children: ReactNode;
};

export function Card({ title, children }: Props) {}

// нет
export function Card({ title }: { title: string }) {}
```

Имя всегда `Props` — поэтому в файле и живёт один компонент. Если компонентов станет два,
второй тип назвать будет нечем, и это сигнал разделить файл.

**`type`, а не `interface`** (`consistent-type-definitions`). В проекте нет ни одного
случая, где нужно слияние деклараций, а два способа объявить одно и то же снова означают
разнобой.

**Типы React импортируются по имени, а не через пространство имён** (`no-restricted-syntax`
на `React.*`):

```tsx
// да
import type { ReactNode, ElementType } from "react";
type Props = { children: ReactNode; as?: ElementType };

// нет
type Props = { children: React.ReactNode; as?: React.ElementType };
```

`React.ReactNode` работает только за счёт глобального UMD-неймспейса; при
`verbatimModuleSyntax` это лишняя зависимость от глобалов, и в TSX-файле без импорта React
она держится на честном слове.

### Именование пропов

**Проп, повторяющий DOM-атрибут, называется как в DOM**: `className`, `onClick`,
`disabled`, `href`. Своё имя (`classes`, `handleClick`, `isDisabled`) заставляет каждый раз
вспоминать, как оно называется именно в этом компоненте. Линтер такое не проверяет — это
на ревью.

### Хуки

`react-hooks/exhaustive-deps` поднят с предупреждения до **ошибки**: `npm run check`
предупреждения пропускает, а на неполных зависимостях в этом проекте уже дважды ловились
настоящие баги (замороженный `isEndingCompleted`, протухший `hasSave`).

### Стили

Все токены — в `@theme` внутри `src/main.css`; **стандартная шкала Tailwind там
переопределена**, поэтому `text-lg` и подобные значат не то, что в стоковом Tailwind.
Правило простое: если переменная есть в `@theme` — использовать её, если нет — брать
стандартную из Tailwind. Размеры в rem.

Промежуточное значение из макета пишется как arbitrary (`text-[1.375rem]`), но если оно
повторилось больше двух раз — заводится токен в `@theme`. Так появились `--text-base`
(0.9375rem) и `--text-2xs` (0.8125rem).

Порядок классов не обсуждается вручную: его расставляет `prettier-plugin-tailwindcss` при
`npm run format`.

### Неиспользуемые переменные

В `tsconfig` включены `noUnusedLocals` и `noUnusedParameters`, поэтому лишняя переменная
или параметр валит сборку, а не только линт. Для намеренных заглушек — префикс `_`
(`function f(_event)`): его понимают и tsc, и eslint.

### Тесты и язык

Названия тестов (`describe` / `test`) — на английском, всё остальное — UI, контент,
комментарии, документация — на русском. Комментарии внутри тестов тоже русские.
Остальные соглашения по тестам — в разделе [Тесты](#тесты) ниже.

## Как устроен контент

Вся игра описана декларативно в `src/data/gameData.json` — код сцен не содержит.
Сейчас это 3 главы по 3 сцены и 4 концовки.

Сцена состоит из текста и списка вариантов. У варианта есть `nextSceneId`, необязательные
`conditions` (когда вариант вообще показывать) и `effects` (что произойдёт при выборе):

```json
{
  "id": "chapter1_scene1",
  "chapter": 1,
  "title": "Пробуждение",
  "text": "Утро мягко просачивается сквозь занавески…",
  "choices": [
    {
      "id": "c1_s1_choice1",
      "text": "Остаться в постели и прислушаться к утру",
      "nextSceneId": "chapter1_scene2",
      "effects": [
        { "type": "change_stat", "stat": "calm", "delta": 1 },
        { "type": "set_flag", "key": "started_slowly", "value": true }
      ]
    }
  ]
}
```

**Условия:** `flag` (значение флага), `stat_gte` (характеристика не ниже порога),
`has_item` (предмет в инвентаре). Вариант без условий доступен всегда.

**Эффекты:** `change_stat`, `set_flag`, `add_item`, `remove_item`.

**Концовки** — это сцены с `"chapter": 0`, `"isEnding": true` и пустым списком выборов.
Развилка к ним собрана в последней сцене третьей главы: три «сильные» концовки открываются
условием `stat_gte` со значением 5 по соответствующей характеристике, а `ending_balanced`
доступна всегда и работает как запасной вариант.

Чтобы добавить сцену, достаточно дописать объект в `scenes` и сослаться на его `id` из
`nextSceneId` любого варианта — трогать компоненты не нужно.

## Тесты

Тесты на [Vitest](https://vitest.dev/). Запуск:

```bash
npm run test      # watch-режим, для работы
npm run test:run  # однократный прогон, для CI и npm run check
```

`npm run test` без подкоманды остаётся висеть и следить за изменениями — в скриптах и CI
нужен именно `test:run`.

Тестовые файлы лежат **рядом с проверяемым модулем**, а не в отдельной папке:

```
src/engine/conditions.ts
src/engine/conditions.test.ts
src/engine/effects.ts
src/engine/effects.test.ts
```

Так их подхватывает и Vitest (дефолтный glob `**/*.{test,spec}.ts`), и `tsc -b` — в
`tsconfig.app.json` указано `"include": ["src"]`, поэтому тесты за пределами `src/`
остались бы без проверки типов. В сборку они не попадают: Vite бандлит только то, что
достижимо от точки входа.

Что покрыто:

- `engine/conditions.test.ts` — доступность вариантов: `flag`, `stat_gte`, `has_item`,
  объединение условий по И, граница `>=`
- `engine/effects.test.ts` — применение последствий: все четыре типа эффектов, порядок
  применения, иммутабельность состояния
- `engine/gameEngine.test.ts` — переходы между сценами, разблокировка глав и концовок,
  подбор картинки, ошибки на несуществующих сценах
- `utils/saveLoad.test.ts` — сохранение и загрузка, поведение при испорченном JSON
- `data/gameData.test.ts` — целостность контента: все ссылки на сцены существуют, нет
  недостижимых сцен и тупиков, пути к картинкам ведут на `/images/`
- `app/App.test.ts` — навигация: маршруты, редирект с `/game` без сохранения, кнопка
  «Назад» по истории (Testing Library + `MemoryRouter`)

Соглашения: названия тестов (`describe` / `test`) на английском, комментарии внутри — на
русском. `expect` и `test` импортируются явно из `vitest`, без `globals: true` — поэтому
отдельный конфиг Vitest не нужен, а типы в тестах проверяются наравне с остальным кодом.
`saveLoad` подменяет `localStorage` заглушкой в памяти; тестам навигации DOM включается
пофайлово докблоком `// @vitest-environment jsdom`, так что тесты логики его не поднимают.

Ещё не покрыто: остальные компоненты по отдельности и сквозные сценарии в браузере.

## Сохранения

Прогресс пишется в localStorage под ключом `quiet-good-life-save` после каждого выбора.
При наличии сохранения главное меню показывает «Продолжить», иначе — «Старт».
