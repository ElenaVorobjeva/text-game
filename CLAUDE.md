# CLAUDE.md

Заметки по проекту для Claude Code. Здесь только то, что неочевидно из кода.

## Команды

```bash
npm run dev       # Vite dev-сервер, порт 5173
npm run check     # типы + линт + формат + тесты (всё, что гоняет CI)
npm run build     # check + vite build
npm run test:run  # однократный прогон тестов
```

`npm run check` — то, чем проверять работу перед сдачей. Отдельные шаги: `typecheck`,
`lint`, `format:check`, `test:run`.

**`npm run test` — это watch-режим**, он не завершится сам. В скриптах и проверках всегда
`test:run`.

Для визуальной проверки есть `.claude/launch.json` (конфигурация `dev`) — запускать сервер
через preview_start, а не через Bash.

## Соглашения по коду

Бо́льшая часть проверяется линтером: нарушение валит `npm run check`, помнить наизусть не
нужно. Правила лежат в блоке `files: ["src/**/*.{ts,tsx}"]` в
[eslint.config.js](eslint.config.js).

Проверяется автоматически:

| Правило                       | Что запрещено                                                   |
| ----------------------------- | --------------------------------------------------------------- |
| `func-style`                  | `const Foo = () => {}` — объявлять через `function Foo() {}`    |
| `no-restricted-syntax`        | `export default` — только именованный экспорт                   |
| `no-restricted-syntax`        | объектный тип прямо в параметре — выносить в `type Props`       |
| `no-restricted-syntax`        | `React.ReactNode` и прочие `React.*` — импортировать из `react` |
| `no-restricted-syntax`        | шаблонная строка в `className` — склеивать через `cn()`         |
| `consistent-type-definitions` | `interface` — в проекте только `type`                           |
| `import-x/order`              | произвольный порядок импортов — чинится `eslint --fix`          |
| `react-hooks/exhaustive-deps` | неполные зависимости хуков (здесь это ошибка, не warning)       |

Правило про `func-style` смотрит только на объявления: стрелки в колбэках
(`onClick={() => …}`, `useCallback`, `map`) не запрещены и запрещаться не должны.

Линтер выразить не может, держать в голове:

- **Тип пропсов называется `Props`** и лежит прямо над компонентом. Отсюда следует **один
  компонент на файл**, имя файла совпадает с именем компонента: два компонента в одном
  файле сделали бы имя `Props` невозможным.
- **Проп, повторяющий DOM-атрибут, называется как в DOM** — `className`, `onClick`,
  `disabled`, а не `classes`, `handleClick`. Своё имя заставляет каждый раз вспоминать,
  как оно тут называется.
- **Взаимоисключающие пропы описываются union'ом, а не набором опциональных полей.**
  У [Link](src/components/base/Link.tsx) ссылке обязателен `href`, кнопке — `onClick`;
  Пока пропы были просто опциональными, `<Link type="button">` без `onClick`
  компилировался в мёртвую кнопку. [Card](src/components/base/Card.tsx) наоборот не знает
  видов карточек: страница передаёт готовую `label`, а закрытость — строкой `closedLabel`.
- **Приведение к boolean — через `Boolean(...)`**, не `!!`. Смысл тот же, но в проекте
  должна быть одна форма.
- **Логику развилок держать в JSON**, а не в компонентах (см. «Архитектура»).

## Главное про стили: @theme переопределяет шкалу Tailwind

Проект на Tailwind v4, все токены заданы в `@theme` внутри [src/main.css](src/main.css).
**Стандартная шкала размеров переопределена**, поэтому привычные значения Tailwind тут врут:

| Класс            | В этом проекте     | В стоковом Tailwind |
| ---------------- | ------------------ | ------------------- |
| `text-2xs`       | 0.8125rem          | не существует       |
| `text-base`      | 0.9375rem          | 1rem                |
| `text-xs`        | 1rem               | 0.75rem             |
| `text-sm`        | 1.125rem           | 0.875rem            |
| `text-md`        | 1.875rem           | не существует       |
| `text-lg`        | 2rem               | 1.125rem            |
| `text-xl`        | 3.25rem            | 1.25rem             |
| `text-2xl`       | 5.25rem            | 1.5rem              |
| `rounded-*`      | 0.375/0.5/0.625rem | 0.25/0.375/0.5rem   |
| `leading-normal` | 1.4                | 1.5                 |

`leading-free` (1.6) — кастомный, стокового аналога нет.

Ширины блоков контента тоже вынесены в токены (`--container-*` → утилиты `max-w-*`),
названия по роли, чтобы значения из макета не расползались по компонентам магическими
числами:

| Класс          | Значение | Где                       |
| -------------- | -------- | ------------------------- |
| `max-w-text`   | 37.5rem  | `Description`             |
| `max-w-intro`  | 40rem    | вступление в главном меню |
| `max-w-scene`  | 43.75rem | `SceneView`, `ChoiceList` |
| `max-w-banner` | 51.25rem | `Image`                   |
| `max-w-grid`   | 56.25rem | `CardGrid`                |

Имена намеренно не пересекаются со стоковыми: `max-w-prose` и `max-w-sm` остаются
тайлвиндовскими, и список переопределений не растёт.

Правило при вёрстке: **если переменная есть в `@theme` — использовать её**, если нет —
брать стандартную из Tailwind. Размеры задавать в rem. Промежуточное значение из макета
пишется как arbitrary (`text-[1.375rem]`), но **если оно повторилось больше двух раз —
завести токен в `@theme`**: так из повторявшихся `text-[0.9375rem]` и `text-[0.8125rem]`
появились `--text-base` и `--text-2xs`.

### Склейка классов: только через cn()

Классы собираются функцией `cn()` ([src/utils/cn.ts](src/utils/cn.ts)) — это `clsx` плюс
`tailwind-merge`. Шаблонные строки в `className` запрещены линтером, и на то две причины:
`clsx` выбрасывает `undefined` (иначе в разметку уезжал класс `undefined`), а
`tailwind-merge` детерминированно разрешает конфликт — переданный снаружи `p-8` перебивает
`p-6` из компонента, а не полагается на порядок в CSS.

В `cn.ts` есть `extendTailwindMerge` с ручным списком: `leading-free` и `animate-*`
придуманы этим проектом, их имён нет в стоковом Tailwind, и без регистрации
`tailwind-merge` не считает их конфликтующими. **Добавляя такой токен в `@theme`, добавь
его и в этот список** — остальную шкалу (`--text-*`, цвета, `--container-*`) библиотека
разбирает сама, потому что имена совпадают по форме со стоковыми.

Порядок классов внутри `cn()` расставляет `prettier-plugin-tailwindcss` — для этого в
`.prettierrc` указано `"tailwindFunctions": ["cn"]`, без этой строки сортировка внутри
вызова не работает.

### Цвета

`black` `#080a14` (фон), `light-blue` `#dcdfe9` (основной текст), `grey-blue` `#767fa0`
(вторичный текст), `grey` `#c3c7db`, `dark-blue` `#12172a` (текст на белых кнопках),
`grey-60` / `grey-160` — полупрозрачные белые для рамок.

Шрифты: `font-heading` (Marck Script, заголовки-надписи), `font-title` (Playfair Display,
заголовки сцен), `font-text` (Inter, весь остальной текст).
Шрифты самохостятся через пакеты `@fontsource*` (импорты в начале main.css), а не с Google
Fonts. Имена семейств у вариативных шрифтов оканчиваются на `Variable`
(`"Inter Variable"`) — при смене пакета проверять имя в `@theme` и в `ImagePlaceholder`.

### Анимации

`animate-fade-up` и `animate-scale-in` объявлены через `--animate-*` в `@theme`.
В конце main.css есть блок `prefers-reduced-motion`, который гасит их вместе с
`animation-delay` — без сброса задержки кнопки выбора остались бы невидимыми
(`animation-fill-mode: both`).

Экраны переигрывают анимацию через `key={scene.id}` — без ключа React переиспользует
DOM-узел и анимация проигрывается только при монтировании.

## Архитектура

Маршрутизация на react-router (`HashRouter`) в [src/app/App.tsx](src/app/App.tsx):
`/` — каталог игр ([GameCatalogPage](src/pages/GameCatalogPage.tsx)), `/:gameId/*` —
оболочка выбранной игры ([GameRoute](src/app/GameRoute.tsx)), всё лишнее (`*`) редиректит
на `/`. Общая обёртка страницы (фон, шрифт, `min-h-screen`) живёт в `App`; страницы её не
дублируют.

`GameRoute` берёт `gameId` из URL, находит игру в реестре
([src/data/games.ts](src/data/games.ts)) и монтирует её `GameProvider` с `key={gameId}`
(смена игры = новое состояние); неизвестный `gameId` уводит на `/`. Внутри —
[GameLayout](src/app/GameLayout.tsx): вложенные роуты экранов игры (`index` = меню, `game`,
`chapters`, `endings`) и шапка (на меню игры свёрнута до ссылки «К играм»).

`HashRouter`, а не `BrowserRouter`: игра — статика, а адреса вида `/#/game` работают на
любом хостинге без правил переписывания на сервере. Роут — это **экран, а не сцена**:
текущая сцена хранится в состоянии, в URL её нет — иначе кнопка «Назад» откатывала бы
адрес, не откатывая состояние игры.

`/:gameId/game` защищён: без сохранения (`hasSave === false`) редиректит в меню игры
(`/:gameId`), чтобы прямой заход по ссылке не начинал игру втихую. Пути экранов строятся
хелпером `gamePath(gameId, sub)` — префикс `gameId` не размазывается по компонентам
строками. Навигацию делают сами страницы через `useNavigate()`; `EndingView` пока остаётся
на пропсах-колбэках, `GamePage` для него — адаптер. Кнопка «Назад» на экране глав —
`navigate(-1)` по истории (с запасным путём в меню игры, если истории нет:
`location.key === "default"`).

Состояние игры — один контекст ([src/state/gameProvider.tsx](src/state/gameProvider.tsx)),
доступ через хук `useGame()`. Провайдер монтируется на активную игру: `GameRoute` передаёт
ему `gameData` из реестра, а движок строится из этих данных — `createGameEngine(gameData)`
(см. ниже). `gameId` активной игры (`= gameData.meta.id`, родом из URL) отдаётся наружу —
им адресуются сохранение и профиль. `loadGame`/`createInitialGameState` вызываются в
ленивых инициализаторах `useState` — не в теле рендера, потому что `loadGame` может писать
в localStorage.

Действия провайдера, меняющие экран, возвращают `boolean` (`continueGame`, `chooseChapter`):
навигировать только при `true`, иначе состояние не изменилось, а переход бы случился.

**Всё пользовательское — один объект в localStorage** под ключом `quiet-good-life-user`
([src/user/userStorage.ts](src/user/userStorage.ts)): `games: Record<gameId, { completedEndings,
progress }>`. Под мультиигры и концовки, и сохранения разложены по `gameId`. Версий и миграций
нет намеренно — игра ещё не вышла к людям; при смене формы старые данные просто отбрасываются.

Слои над этим объектом разделены по знанию об игре:

- **`userStorage` — game-agnostic хранилище.** Держит прогресс как непрозрачный `GameStateData`,
  движок не импортирует. Профиль через `useUser()`; API разрезан по `gameId` (`completeEnding(gameId,
type)` и пр.), сам id провайдеру даёт `useGame()`. **Единственный источник правды о собранных
  концовках — провайдер**; производные вроде `isEndingCompleted` в модуле не дублируются.
- **`saveLoad` — надстройка, знающая движок.** Только читает: `loadGame` валидирует прогресс
  против контента (форма состояния, `sceneExists`, добор недостающих полей). Запись и стирание
  прогресса одной игры идут через `UserProvider` (`saveProgress` / `clearProgress`), а в тестах —
  через `writeProgress` / `clearProgress` из `userStorage`. `clearAllSaves` стирает прогресс всех игр
  (нужно `ErrorBoundary`, который активной игры не знает), не трогая концовки.

Политика отказа одна: непригодные данные отбрасываются, причина уходит в `console.warn` — потеря
прогресса или концовок не должна происходить молча. Битый JSON всего объекта не чистится (перезапишется
при следующей записи); негодное сохранение конкретной игры `saveLoad` обнуляет точечно.

Загрузка данных имитирует поход на сервер: [ProfileGate](src/app/ProfileGate.tsx) держит фейковый таймаут
(3 с) и показывает полосу загрузки ([Loader](src/components/base/Loader.tsx)) по центру, а провайдеры
монтируются уже после. Когда появится настоящий бэкенд, здесь будет реальный `fetch`.

Контент полностью декларативный: каждая игра — свой `GameData`-JSON в `src/data/`
(флагман — [quietGoodLife.json](src/data/quietGoodLife.json)). Реестр
[src/data/games.ts](src/data/games.ts) — единственное место, знающее, какие игры есть
(`games`, `getGameData`, `gameList`); сюда же встанет ленивая загрузка контента.

Движок в `src/engine/` **строится из данных игры**, а не завязан на одну:
`createGameEngine(gameData)` возвращает функции, замкнутые на переданный контент
(`getSceneById`, `sceneExists`, `makeChoice`, `createInitialGameState`, `getSceneImage`…);
чистые функции (`enterChapter`, `canEnterChapter`, `getAvailableChoices`) остаются
свободными. `conditions.ts` фильтрует варианты (`flag`, `stat_gte`, `has_item`),
`effects.ts` применяет последствия (`set_flag`, `change_stat`, `add_item`, `remove_item`).

Логику развилок держать в JSON, а не в компонентах.

## Тесты

Vitest, файлы лежат рядом с модулем (`effects.ts` → `effects.test.ts`). Отдельной папки
для тестов нет намеренно: `tsconfig.app.json` содержит `"include": ["src"]`, поэтому тесты
за пределами `src/` выпали бы из `tsc -b`.

Глобального конфига Vitest нет: `describe` / `expect` / `test` импортируются явно, без
`globals: true`. Тесты логики (движок) идут в окружении node. Тестам компонентов нужен DOM
— его включает **пофайловый** докблок `// @vitest-environment jsdom` в начале файла
([src/app/App.test.tsx](src/app/App.test.tsx)), а не глобальная настройка: так тесты
движка не платят за поднятие jsdom. Тесты со страницами оборачиваются в `MemoryRouter`
(`initialEntries` задаёт стартовый роут и историю для проверки «Назад»); Testing Library
при `globals: false` не чистит DOM сама — нужен `afterEach(cleanup)`.

`saveLoad` тестируется без jsdom: `localStorage` там подменяется заглушкой в памяти через
`vi.stubGlobal`.

Навигация покрыта [src/app/App.test.tsx](src/app/App.test.tsx): каталог и выбор игры,
guard `/:gameId/game`, кнопка «Назад» по истории.

Новый тест стоит проверять на «ложную зелень»: сломать проверяемый код и убедиться, что
тест упал. Тест, который проходит при сломанной реализации, бесполезен.

## Грабли

**Пути к картинкам.** В данных игры (`quietGoodLife.json` и другие в `src/data/`) должно быть
`/images/…`, а не `/public/images/…`.
Второй вариант работает в `npm run dev` (Vite отдаёт файлы с диска) и отваливается 404 в
проде, потому что `public/` копируется в корень `dist/`. Ловится только сборкой.

**Строгий tsc.** Включены `strict`, `noUnusedLocals` и `noUnusedParameters`, поэтому
неиспользуемая переменная или параметр валит сборку, а не только линт. Для намеренных
заглушек — префикс `_`: его понимает и tsc, и eslint (в `eslint.config.js` для
`no-unused-vars` заданы `argsIgnorePattern` / `varsIgnorePattern`).

**Высота игрового экрана.** Не вешать `h-screen` + `overflow-hidden` на игровой экран:
на низких окнах последние варианты выбора обрезаются без скролла и игру нельзя пройти.
Сейчас там `flex grow flex-col`, страница скроллится штатно.

**Картинки глав уже содержат название главы**, нарисованное внутри. Плашку с подписью
поверх баннера не добавлять — будет дублирование.

## Известные незакрытые места

Механика перехода к главе уже реализована: `chooseChapter(chapterId)` в gameProvider
